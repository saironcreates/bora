The Problem
worth solving

Marketplace sellers were drowning in paperwork. Each sale on Trendyol, Hepsiburada, or Amazon Turkey required a manually generated e-invoice — filed within 7 days by law. With hundreds of daily orders, sellers were spending 3–4 hours a day just on invoicing, or hiring dedicated staff for a task that should be invisible.

The existing tools were either too complex (full ERP systems) or too basic (simple PDF generators). Nobody had designed invoicing specifically for marketplace sellers — people who care about their products, not tax compliance software.

"I sell 200 items a day. I don't have time to think about invoices — they should just happen."

eInvoice was designed from the ground up for this persona. Connect your marketplace API, set your rules once, and never think about invoicing again. The entire UX was built around one principle: if the user has to do it manually, we failed.

Challenges

Complex rules,
simple interface

⚖️
Legal Complexity
Turkish e-invoice law (e-Fatura / e-Arşiv) has dozens of edge cases — different rules for B2B vs B2C, VAT thresholds, cancellation windows. All this had to become invisible to the end user while staying 100% compliant.
🔗
Multi-Marketplace Sync
Each marketplace (Trendyol, Hepsiburada, Amazon TR, n11) has a different API structure, order schema, and timing. Designing a unified data model that abstracts these differences — without losing seller-specific details — was the core UX challenge.
🎯
Trust & Confidence
Sellers were handing over their tax compliance to an algorithm. The UI had to communicate reliability and accuracy at every step — real-time status, clear audit trails, and one-tap manual override — so users felt in control, not anxious.

Project Timeline

16 weeks,
research to launch

Week 1–3
Research & Discovery
Interviewed 18 marketplace sellers across Trendyol, Hepsiburada, and Amazon TR. Mapped the current invoicing workflow end-to-end. Identified 7 key pain points — the biggest: sellers had no idea when an invoice failed GİB validation.
Week 4–5
IA & User Flows
Defined information architecture for a 3-role system (Seller, Accountant, Admin). Mapped 12 core user flows — from first connection to daily invoice review. Validated flows in low-fidelity with 6 participants.
Week 6–8
Design System Foundation
Built a full component library in Figma: 80+ components, 3 state variants each (default, hover, disabled), dark theme optimised for data-dense screens. Token system spans 6 categories: color, spacing, type, radius, shadow, motion.
Week 9–13
High-Fidelity Design
Full hi-fi screens for all core flows: dashboard, invoice list, rule builder, seller onboarding, and reporting. Interactive prototype in Protopie for the rule engine — the most complex interaction surface in the product.
Week 14–16
Testing & Dev Handoff
3 rounds of usability testing — iterated on the rule builder after round 1 revealed sellers didn't understand "condition" vs "action" terminology. Final handoff includes annotated specs, motion guidelines, and a Storybook-ready component doc.
