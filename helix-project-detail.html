01

Design at
enterprise scale

Most design systems start as a UI kit and grow into bureaucracy. Helix started from the opposite direction: what does an engineering team actually need to move fast without breaking consistency? The answer isn't more components — it's better foundations, precise documentation, and a system that punishes inconsistency at the token level, not in design review.

The brief was an enterprise SaaS product with a design debt crisis: six product teams building in parallel, three different button implementations, no shared colour system, and a dark mode hand-coded per component. The task was to unify everything without disrupting in-flight shipping teams.

"A design system is infrastructure. It should be invisible when it works and obvious when it doesn't — like a grid."

Helix was built token-first: colour, spacing, typography, and motion defined as JSON tokens synced to both Figma variables and CSS custom properties. The 120+ React components in Storybook consume only tokens — never raw values. Dark and light mode is a single token swap.

Challenges

120 components,
zero raw values

🌓
Dark / Light Without Duplication
Both themes needed to feel intentionally designed, not just inverted. Used a semantic token layer (color.surface.primary, color.text.secondary) above the primitive palette — components reference semantic tokens only, so theme switching is a JSON swap with zero component-level changes.
♿
WCAG AA Everywhere
Every colour combination in the system was validated against WCAG AA (4.5:1 minimum contrast). Built a custom Figma plugin that runs contrast checks on all component variants automatically during the CI step — a failing contrast ratio blocks merge to main.
🔄
Migration Without Disruption
Six product teams couldn't stop shipping to migrate. Built a compatibility shim layer that maps old class names and props to the new token system — teams could adopt Helix incrementally, component by component, without a big-bang migration sprint.
01
Token Architecture
Three-tier token hierarchy: primitives (raw values), semantics (role-based names), and components (component-specific references). Nothing references primitives directly — all values flow through the semantic layer, making global theme changes a single file edit.
